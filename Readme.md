# Проект представляет собой комплекс автоматизированного тестирования (Python + Selenium) для веб-сервиса «Stellar Burger» — сервиса по сборке и заказу бургеров. 
Автотесты охватывают ключевую пользовательскую логику работы с интерфейсом и проверяют корректность динамических элементов в реальном времени.

## Охват тестирования и проверенный функционал

### 1. Главная страница («Конструктор»)
Проверено 5 основных пользовательских сценариев:
- **Навигация** – переходы между разделами «Конструктор» и «Лента заказов».
- **Работа с ингредиентами** – открытие модального окна с деталями ингредиента, его закрытие.
- **Формирование заказа** – увеличение счетчика ингредиента при добавлении в конструктор (drag-and-drop).

### 2. Лента заказов
Проверено 3 критических бизнес-правила:
- **Динамические счетчики** – увеличение счетчиков «Выполнено за всё время» и «Выполнено за сегодня» при оформлении заказа.
- **Real-time отображение** – появление номера нового заказа в разделе «В работе» сразу после оформления.

**Итого:** Разработано **8 автоматизированных UI-тестов**, которые полностью покрывают основной пользовательский путь: от выбора ингредиентов до отслеживания статуса заказа в реальном времени.

## Технический стек и архитектура

### Фреймворки и библиотеки
1. **`pytest`** – основной фреймворк для организации тестов:
   - Фикстуры для подготовки окружения (`login_user`, `driver`, `main_page`).
   - Четкая структура тестовых классов (`TestMainPage`, `TestOrderFeed`).

2. **`Selenium WebDriver`** – для автоматизации браузера:
   - Поддержка **Google Chrome** и **Mozilla Firefox**.
   - Навигация, клики, drag-and-drop, ожидания элементов.

3. **`Allure-pytest`** – для отчетности:
   - Каждый тест имеет понятный заголовок (`@allure.title`).
   - Детальное описание шагов (`@allure.description`).
   - Визуализация результатов в виде красивого отчета.

### Паттерны и подходы
1. **Page Object Model (POM)** – основной архитектурный паттерн,
2. **Явные ожидания (Explicit Waits)** – стабильность тестов,
3. **Нормализация данных** – для надежных проверок,
4. **Изоляция тестов** – независимость выполнения:
   - Каждый тест создает нового пользователя (`login_user` фикстура).
   - Чистое состояние браузера для каждого теста.

## Любопытный факт: 
Номер заказа пользователь получаетв 5-значном формате, а номер заказа в окнах выводится в 6-значном, с "0" в начале. В итоге сервис работает нормально,
но заведён баг на несоответствие фактического номера заказа ожидаемому ))

## Ценность проделанной работы

### 1. **Обеспечение качества ключевых функций**
   - Автоматически проверяется логика, критичная для бизнеса: формирование заказа, обновление статистики, отображение заказов в реальном времени.
   - Ручная проверка этих сценариев занимала бы 10–15 минут на каждый прогон; автоматизация сокращает время до 2–3 минут с повышением точности.

### 2. **Раннее обнаружение регрессий**
   - При изменении интерфейса (например, обновлении верстки или логики счетчиков) тесты немедленно покажут, что сломалось.
   - Особенно важно для real-time элементов (лента заказов), где ошибки могут остаться незамеченными при ручном тестировании.

### 3. **Кросс-браузерная совместимость**
   - Тесты гарантируют одинаковое поведение в **Chrome** и **Firefox** — двух основных браузерах для пользователей.
   - Выявляют специфичные для браузера проблемы (например, разное поведение drag-and-drop или отображение модальных окон).

### 4. **Готовый фундамент для масштабирования**
   - Архитектура POM позволяет легко добавлять тесты для новых страниц.
   - Подключение Allure дает готовую систему отчетности, понятную как разработчикам, так и менеджерам.
   - Фикстуры `pytest` позволяют гибко управлять данными тестов (пользователи, заказы, ингредиенты).

### 5. **Профессиональный уровень кода**
   - Четкое разделение ответственности: логика страниц — в `PageObject`, тестовые сценарии — в тестах.
   - Детальные сообщения об ошибках (с указанием «было/стало»), что ускоряет дебаг.
   - Обработка крайних случаев (например, проверка, что номер заказа не равен временному значению «9999»).

## Заключение
Данный проект автотестов заменяет трудоемкое ручное тестирование критических сценариев, обеспечивает стабильность ключевых функций при изменениях кода и служит документацией того, как система должна работать.
Сломанная навигация, некорректные счетчики заказов, отсутствие real-time обновлений — все это напрямую влияет на доверие пользователей и конверсию в заказы. Автоматизированная проверка этих функций перед каждым релизом минимизирует риск выпуска сломанной функциональности в продакшен.


## Файлы:

- allure-results-chrome - каталог с отчетом о тестировании в Google Chrome
- allure-results-firefox - каталог с отчетом о тестировании в Mozilla Firefox

- data/ingredients.py - файл с данными ингредиентов
- data/urls - файл с URL сервиса и ручками
- data/user_data.py - файл с методами генерации данных для регистрации

- locators/locators.py - файл с локаторами элементов сервиса

- pages/base_page.py - файл с базовыми методами взаимодействия
- pages/login_page.py - файл с методами взаимодействия со страницей авторизации
- pages/main_page.py - файл с методами взаимодействия с главной страницей
- pages/order_feed_page.py - файл с методами взаимодействия со страницей ленты заказов

- tests/test_main_page.py - файл с проверками основного функционала
- tests/test_order_feed.py - файл с проверками ленты заказов

### Запуск в Chrome (по умолчанию)
pytest tests -v   

### Запуск в Firefox
pytest tests --browser=firefox -v   

### Запуск с отчётами в Chrome:
- pytest --browser=chrome --alluredir=allure-results-chrome
- allure serve allure-results-chrome

### Запуск с отчётами в Firefox:
- pytest --browser=firefox --alluredir=allure-results-firefox
- allure serve allure-results-firefox

### Создать общий отчет из обоих запусков
allure serve allure-results-chrome allure-results-firefox

### Перед работой с репозиторием требуется установить зависимости
pip install -r requirements.txt
